# 调研报告 001（2026-11-01）— 与 imgbb 同构的开放图床/图站调研

> 日期：2026-11-01
> 调研方式：**网络搜索 API 检索 + 官方文档/第三方工具说明核实**（本机沙箱无出网，curl 实测 baidu/github 均返回 000）
> 前置报告：`2026-08-12-001-图床替代品评估.md`（已有 9 站实测矩阵）、`2026-10-08-001-多图站适配体检.md`（现行 `src/sites` 体系）
> 目标：找「网站结构类似 imgbb、开放、可做类似扩散检索与相册下载」的站

## 一、imgbb 适配器的 4 大结构特征（判定基准）

对照 `设计文档/模块边界.md` imgbb 专规：

1. **用户主页公开可枚举**：`https://{username}.imgbb.com`，无需登录
2. **相册生态**：`/albums` 列表（分页）+ `ibb.co/album/{ID}` 详情
3. **关注体系**：`/following`、`/followers` 公开页（支撑 FP-005 扩散检索的图边）
4. **结构化数据**：`data-object` JSON 内 `image.url` 即原图，后台 fetch 即可解析

> 关键取舍：**「关注关系」是扩散检索的前提**，只有具备它的站才可能替代 imgbb 的扩散能力；只有相册没有关注的站，只能提供「用户级批量下载」。

## 二、本次核实到的候选（按价值排序）

### 2.1 Chevereto 实例群（最可能低成本复活）

数据来源：[webatla Chevereto 站点统计](https://webatla.com/technology/chevereto)（2026-10-31，846 个在用实例）

| 实例 | HTTP | 运营关联 | 备注 |
|------|------|---------|------|
| `freeimage.host` | 200 | Reddit / YouTube / Twitter 账号 | 项目 FP-007 曾适配后废弃 |
| `fotoku.host` | 200 | **与 freeimage 同一套社交账号（同运营方）** | 结构同构 |
| `imgstore.io` | 200 | 无社交信息 | 2024 年建站 |
| `imgstock.io` | 200 | 无社交信息 | 2025 年建站 |
| `videovssylku.ru` | 200 | Telegram 机器人 | 俄语实例 |

结构事实（来自前置报告 001 的实测 + Chevereto 标准行为）：

- 探索页 `https://{host}/explore` 为 **SSR**，约 45 图/页，`?ajax=1&list=images&sort=date-added-desc&page=N` 分页有效
- `data-object` JSON 顶层字段与 imgbb 高度同构：`id_encoded / image / thumb / name / title / display_url / extension / filename / height / width / url_viewer / url_short / url`
- 图片 CDN：`iili.io`
- 用户路由：`/{user}`、`/{user}/albums`、`/{user}/followers`、`/{user}/following`、`/{user}/liked`（均 200，**内容为 JS 动态加载**，需 AJAX 端点）
- 差异：`data-object` **无 user 字段**（属主需从图片页取）；匿名上传（Guest）占主导

**价值**：一个解析器 + 多域名配置即可覆盖 4 个活跃实例；`归档/freeimage-2026-08-13-废弃归档/` 内有完整实现可复用。

### 2.2 Pixelfed 联邦实例群（扩散检索最完整）

数据来源：[Pixelfed API 文档 — Accounts](https://developers.pixelfed.org/api/accounts)

已核实的标准端点（Mastodon 兼容）：

| 端点 | 用途 |
|------|------|
| `GET /api/v1/accounts/{id}/statuses` | 用户全部帖子（图片/视频，分页） |
| `GET /api/v1/accounts/{id}/followers` | 粉丝列表 |
| `GET /api/v1/accounts/{id}/following` | 关注列表 |
| `GET /api/v1/collections` | 相册（Pixelfed 独有） |
| `GET /api/v1/discover/*` | 发现页 |

账号对象含 `followers_count / following_count / statuses_count / note / url`。
用户主页 URL：`https://{instance}/{username}`。

**价值**：唯一「关注关系可编程枚举、无需解析 HTML」的形态，可直接喂给现有扩散引擎（BFS + 入度统计）。

限制：内容以摄影/生活为主，成人内容取决于实例政策；部分端点可能需 access token（待实测）；多实例需要「实例列表」这一新配置概念（现有 `src/sites` 是单域名模型）。

### 2.3 ImageFap（与现有业务最贴）

数据来源：[imagefap-dl 官方 usage](https://github.com/patrickkfkan/imagefap-dl)

| 目标 | URL |
|------|-----|
| 用户全部图库 | `https://www.imagefap.com/profile/{username}/galleries` |
| 用户文件夹 | `/profile/{user}/galleries?folderid={id}`、`/organizer/{folderId}/{slug}` |
| 单图库 | `/gallery/{galleryId}`、`/gallery.php?gid=`、`/pictures/{id}/{slug}` |
| 用户收藏 | `/showfavorites.php?userid={userId}&folderid={id}` |

- 反爬：工具默认**页间 2 秒**，低于此会 `Too many requests`（项目已有 `throttle` 机制可复用）
- 有 `--seq-filenames`（按显示顺序编号）→ 与项目「命名顺序 = 抓取顺序」的约定一致
- 关注/好友关系：**待实测**（接口文档未覆盖）

### 2.4 Erome（结构最简，无关注）

数据来源：[EromeDownloader README](https://github.com/Lysagxra/EromeDownloader)

- 用户主页：`https://www.erome.com/{username}`（可提取全部专辑链接）
- 专辑：`https://www.erome.com/a/{albumId}`
- **无关注关系** → 只能做「用户级批量下载」

### 2.5 Bunkr（只有专辑，签名 2 小时过期）

数据来源：[bunkr-api 文档](https://pypi.org/project/bunkr-api/)

- 专辑页内含 `window.albumFiles` JS 数组（可直接解析）
- 支持搜索 / trending / 创作者名检索
- **CDN 链接 2 小时过期**，需实时 mint → 与「先抓 URL 再排队下载」的模型冲突
- 无用户主页/关注

### 2.6 已排除（本次复核仍不适用）

| 站点 | 排除理由 |
|------|---------|
| imgur、flickr | 国内被墙（前置报告实测 `000`） |
| postimages.org | 无用户名/相册/关注，hash 不可枚举 |
| pixhost.to、imagebam.com、imagevenue、imx.to、vipr.im | 无公开用户生态，仅匿名图链 |
| imgpile.com | 有 `/u/{user}` 但公开内容极少 |
| freeimage.host 本体 | 曾适配后废弃；**同运营实例（fotoku/imgstore/imgstock）可替代** |

## 三、与 imgbb 的结构对照

| 能力 | imgbb（现状） | Chevereto 系 | Pixelfed | ImageFap | Erome | Bunkr |
|------|--------------|--------------|----------|----------|-------|-------|
| 用户主页公开 | ✅ 子域 | ✅ `/{user}` | ✅ `/{user}` | ✅ `/profile/{user}` | ✅ `/{user}` | ❌ |
| 相册列表分页 | ✅ `/albums?page=N` | ✅ AJAX 端点 | ✅ collections/statuses | ✅ `/galleries` | ✅ 用户页 | ❌ |
| 相册详情可枚举 | ✅ `data-object` | ✅ SSR `data-object` | ✅ statuses JSON | ✅ 图库页 | ✅ 专辑页 | ✅ `albumFiles` |
| **关注关系** | ✅ `/following` | ⚠️ 路由存在、JS 加载 | ✅ **标准 API** | ⚠️ 待核实 | ❌ | ❌ |
| 结构化数据 | ✅ JSON in HTML | ✅ 同构 | ✅ 纯 JSON API | ⚠️ HTML | ⚠️ HTML | ⚠️ JS 变量 |
| 原图直链 | ✅ `i.ibb.co` | ✅ `iili.io` | ✅ 媒体 URL | ⚠️ 待核实 | ⚠️ CDN | ⚠️ 签名 2h |
| 反爬强度 | 弱（referer 需源页注入） | 弱（Cloudflare 前置） | 很弱（标准 API） | **强**（2s/页） | 中 | 中（TLS 指纹） |
| 适配成本（对照 `src/sites`） | — | **低**（有归档实现 + 多域名） | 中（需多实例模型） | 中高（节流 + 页面解析） | 中 | 中（签名刷新） |

## 四、建议优先级

| 优先级 | 事项 | 理由 |
|-------|------|------|
| **P0** | Chevereto 实例群（imgstore.io / imgstock.io / fotoku.host / freeimage.host） | 复用归档解析器 + 多域名；探索页 SSR 已证实 |
| **P1** | ImageFap（用户全部图库 + 单图库） | 内容生态与现有 9 站最接近，天然有用户维度 |
| **P2** | Pixelfed 实例（followers/following/statuses） | 「标准 API + 关注图」的架构验证，可喂扩散引擎；内容生态偏摄影 |
| 可选 | Gelbooru/Danbooru 系（tag 扩散） | 若无关注关系可用，用「共享标签」替代「关注边」，复用现有标签云 |
