# FP-005 关注链扩散检索：广域筛选 + 相册检索（草案，待确认）

## 需求

imgbb 无官方相册搜索。通过「关注链扩散」低成本建立**生产者库**（高入度用户），再在生产者库上做**相册关键词检索**。

两个独立模块：

1. **广域筛选（模块 1）**：从起点用户开始，只抓 `following` 列表扩散，统计**入度**（被关注次数），筛出高价值生产者。结果持久化，支持多次不同起点扩散合并、GitHub 手动同步（跨平台）。
2. **相册检索（模块 2）**：读取生产者库 → 取高入度候选 → 逐个抓 `albums` → 关键词匹配 → 列出用户与相册，点击打开对应页面。

## 核心思路（两阶段降本）

- 昂贵操作（albums 确认）后置：只花在高入度候选上
- 廉价信号（following）前置：扩散时只抓 following（每人 1~3 页请求），用入度粗筛
- 生产者 = 被多次标注的用户（幂律分布假设，同主题网络内成立）

## 综合评分机制（确认后排序）

> 相册数只有抓 albums 后才可知，因此评分发生在「确认」阶段之后，检索之前。

```
综合评分 = w1 × 归一化(入度) + w2 × 归一化(相册数)    // w1+w2=1，默认 0.6/0.4，可配置
归一化 = 对数归一化 log(1+x)/log(1+max)  // 入度呈幂律，对数归一化避免大 V 碾压
```

- 纯入度会被「大 V 观察者」（粉丝多但不发相册）污染 → 相册数权重校正
- 评分随生产者库积累自动更新（albumsChecked 后补录相册数）
- 权重 w1/w2 在配置区手动调节

## 数据流

```
模块1 起点用户 → following 扩散(每批50+下一批) → 入度表(本地 storage)
        ↓ 手动保存/加载/合并（多起点统合一张表）
        ↓ 手动 GitHub 同步（Contents API，非实时）
模块2 读入度表 → Top-M 候选池 → 分批抓 albums(确认+评分) → 综合评分排序
        → 按百分比区间(手动配置，如 0~10%) + 关键词匹配 → 结果列表(点击打开)
```

### 检索范围 = 手动百分比区间

- 检索不是全量跑，而是基于**综合评分排序后的百分比区间**（如「前 10%」= 0~10%，或「10%~30%」区间）
- 配置：起点百分比 + 终点百分比两个输入框，可配置（如 0~100 默认全量、0~10 只检最高分档）
- 区间内用户仍按批次（每批 50）处理，下一批按钮控制节奏

## 数据模型

### 入度表（生产者库）

```ts
interface ProducerEntry {
  username: string
  inDegree: number          // 被关注次数（不同扩散合并时累加）
  firstSeenAt: number
  lastSeenAt: number
  sources: string[]         // 发现该用户的起点用户（追溯用）
  albumCount?: number       // 模块2 确认后补充
  albumsChecked?: boolean   // 是否已做过 albums 确认
}
```

- 本地：`chrome.storage.local` 键 `producer_db`（`{ version, updatedAt, entries: Record<username, ProducerEntry> }`）
- GitHub：单文件 `imgbb-producers.json`，同步策略**拉取→本地合并入度→推回**（入度累加天然可合并，冲突不丢数据）

### 扩散状态机（模块 1，后台常驻状态）

```
queue: string[]        // 待探索用户（BFS，去重后）
visited: Set<string>   // 已抓过 following 的用户（防环）
inDegree: Map          // 入度统计（当前会话内）
startUser: string      // 本次起点
```

- 无限层级：队列持续扩张，**下一批按钮 = 节奏控制阀**
- 每批 50 人（用户可配置），批内并发 3~5、请求间隔 ~1s（可配置）
- 每用户抓 following **全部分页**（大 V 关注几百人，通常 2~3 页）

## 节流与封禁防护

- 串行批处理 + 批内低并发 + 间隔（可配置）
- **累计请求量显示**（「本会话已请求 n 次」），让用户对风险有感知
- **429 连续检测**：连续 429 达阈值（如 5 次）→ 提示暂停 30s，不硬闯
- 单用户失败跳过（限流/登录墙/404），不中断整批，统计失败数
- GitHub 手动同步（用户确认：非实时，点击才同步，减少请求）

## 消息协议（新增）

| type | 发起方 | 处理方 | 说明 |
|------|--------|--------|------|
| `IMG_DIFFUSE_START` | grabber | background | 广域扩散开始（起点用户，重置状态机） |
| `IMG_DIFFUSE_BATCH` | grabber | background | 处理下一批（队列前 50） |
| `IMG_DIFFUSE_RESULT` | background | grabber | 批结果：入度增量、队列大小、进度、失败数 |
| `IMG_DB_SAVE` / `IMG_DB_LOAD` | grabber | background | 保存/加载本地入度表（合并） |
| `IMG_DB_GITHUB_PUSH` / `IMG_DB_GITHUB_PULL` | grabber | background | 手动同步 GitHub（需配置 repo + token） |
| `IMG_SCORE_BATCH` | grabber | background | 确认+评分：对候选池一批用户抓 albums → 相册数 → 综合评分 |
| `IMG_SCORE_RESULT` | background | grabber | 评分结果：相册数/评分更新、批进度 |
| `IMG_SEARCH_START` | grabber | background | 相册检索：按百分比区间选候选（含已评分用户） |
| `IMG_SEARCH_BATCH` | grabber | background | 检索下一批（区间内候选前 50，未评分先确认再匹配） |
| `IMG_SEARCH_RESULT` | background | grabber | 命中列表（用户+相册名+链接）+ 批进度 |

## UI 形态（imgbb 适配页新增「扩散检索」子标签）

**区域 1 广域筛选**：起点用户名输入 + 「开始扩散」+「下一批」+ 实时进度（本批 x/50、队列 n 人、累计请求、429 提示）

**区域 2 生产者库**：统计（总用户数、入度 Top10）＋ 按钮：保存 / 加载 / GitHub 推送 / GitHub 拉取 + 配置（repo、token）

**区域 3 相册检索**：关键词输入（多个，逗号分隔）＋ 百分比区间配置（起点%/终点%，如 0~10）＋ 权重配置（入度/相册数滑块）＋「开始检索」+「下一批」+ 结果列表（用户名+相册名+链接+评分，点击 `chrome.tabs.create` 打开）

## 配置项（用户可调，默认值）

| 项 | 默认 | 说明 |
|----|------|------|
| 批次人数 | 50 | 每批处理的用户数 |

| 请求间隔 | 1000ms | 批内请求间隔 |
