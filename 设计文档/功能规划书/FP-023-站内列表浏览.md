# FP-023 站内列表浏览（不依赖搜索引擎的发现通道）

> 立项日期：2026-10-07 ｜ 状态：**已交付（路径与分页需实测调优）** ｜ 版本 v0.2.10
> 触发：Google 通道在当前网络环境被 403 拒绝，用户选择「直接抓站点分类/列表页」方向

## 1. 背景

聚合搜索对这批准图站的发现能力原本依赖搜索引擎，但实测三条路都不可靠：

| 引擎 | 实测结果 |
|------|---------|
| Google | 用户网络环境下返回 `403 您的客户端没有权限`（简化 URL `?q=test` 亦被拒 → 与参数无关，属环境/客户端级限制；DSH 侧可访问，Chrome 侧不可 → 疑为 Chrome 代理扩展或安全 DNS 绕过代理 DNS 接管） |
| Bing（国内版） | 可达，但 `site:` 过滤失效 → 返回无关中文结果 |
| Bing（国际版 `ensearch=1`） | 可达，`site:` 仍失效 → 返回完全不相关结果（此类站点未被收录） |
| Yandex | 触发 SmartCaptcha 人机验证 |

结论：**这些站点的站内搜索不能依赖搜索引擎**。而站点自身的分类/列表页一定有内容，是最可靠的发现通道。

## 2. 方案

| 层 | 设计 |
|---|---|
| 定义 | `SiteDef.listPages`：`{ label, path, pageKind?, param?, albumPath? }`；缺省按站点分页方式派生（`query` → `?page=N`、`path-slash` → `/page/N/`、其余 → `/page/N`） |
| 解析 | **不写新解析器**：复用 `parseSitePostLinks`（同域链接提取，已排除分类/标签/分页路径）+ `albumPath`（缺省用 `searchAlbumPath`）收窄 |
| 后台 | `BuonduaService.fetchSiteList(siteId, listUrl, pages, fetchHtmlFn?)`：逐页 fetch + 解析 + 去重；带反爬拦截检测 |
| 兜底 | background 侧：后台 fetch 失败或 0 结果时，**自动降级页面内 fetch**（`BD_FETCH_HTML`，带 Cookie/Referer 穿透反爬），与单相册抓取一致 |
| 消息 | 新增 `BD_FETCH_LIST`；`BuonduaResultKind` 增加 `'list'` |
| 界面 | 「批量抓取其他链接」面板新增「列表浏览」一行：站点下拉（由站点定义派生）+ 列表路径（**可编辑**，预置默认值）+ 页数 + 「抓取列表页」；结果直接载入该面板链接列表 → 复用现有「抓取选中」批量抓取 |

## 3. 默认列表路径（可界面修改）

| 站点 | 默认路径 | 依据 |
|---|---|---|
| hitxhot | `/gallerys/` | 定义中 `searchAlbumPath` 即该路径 |
| kaizty | `/photos/` | 同上 |
| 其余站点 | `/`（根路径） | 无已知分类路径，由用户实测后填写（路径在界面可编辑，无需改代码） |

**设计取向**：我无法在外部访问这些站点（需用户网络环境），因此刻意让路径、页数都可在界面调整 —— 实测发现路径不对时用户可直接改，不必等我改代码发版。

## 5. 不在本范围

- 不做「列表页结构自动探测」（可选后续：贴 URL 自动识别路径与分页并回填）
- 不改 Google 通道（保留为可选通道，受环境限制）
- 不引入新的站点解析器文件（先验证通用规则够不够）
