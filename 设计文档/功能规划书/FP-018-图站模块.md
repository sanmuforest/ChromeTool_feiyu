# FP-018 图站模块（可扩展站点适配）

> 立项日期：2026-10-07 ｜ 状态：阶段 1 已交付（无行为变更重构），阶段 1B 待启动
> 设计目标：把「多页图站适配」从「改代码」变成「改数据」

## 1. 背景与问题

多页图站（buondua / rrwsh / hitxhot / kaizty / jrants / pixibb / cangcuc / phimvuspot / ilovexs）存在两个长期痛点：

1. **这类站点频繁更换域名**。旧结构下换一次域名至少改 4 处，其中 2 处是静默陷阱：
   - `hosts` 列表（不改 → 站点直接识别不到）
   - `searchUrl` 里写死的域名字面量（不改 → 搜索全失败，但抓取仍正常，难以察觉）
   - 图床白名单 `IMG_HOST`（不改 → 无扩展名的 CDN 图片被静默丢弃）
   - buondua / jrants / pixibb 专用解析器里的域名正则
2. **新增站点成本高**：约 10 处改动，横跨 6 个文件，且站点 `id` 成为跨文件隐式契约（`site.id === 'jrants'` 之类分支遍布 service 与 view），漏改任一处即出现局部功能失效。

## 2. 目标（可验收）

| # | 目标 | 验收方式 |
|---|------|---------|
| G1 | 新增站点 = 只加 1 份定义数据，0 行逻辑代码（全新模板才加 1 个具名解析器） | 加一个站，不改 engine/parsers/service/view |
| G2 | 域名变更 = 改 1 处，全链路跟随（识别 / 翻页 / 搜索 / 图床判定 / 文件夹名） | 阶段 1B：UI 改域名后抓取+搜索+命名全通 |
| G3 | 行为零回归 | 新旧实现等价性对比 + 用户实测回归清单 |
| G4 | 站点定义可被 UI 编辑 / 导入导出 / 探测生成 | 定义为纯数据（无函数），可 `JSON.stringify` |

## 3. 设计要点

### 3.1 定义即数据（声明式 DSL）

站点定义（`src/sites/defs/*.ts`）只含数据：域名、正文容器、分页方式、标题清理正则源、图床域、搜索通道、解析器名。原先把「函数」写进配置（`pageUrl` / `baseUrlOf` / `cleanTitle` / `searchUrl` / `rewriteUrl` / `imageUrlClean`）导致配置无法序列化、无法由 UI 编辑、无法由探测生成，故全部改为声明式字段，由 `engine.ts` 编译回等价函数。

### 3.2 域名单一来源

- 域名只允许出现在定义的 `endpoints`（`role: primary | mirror | search`）与 `searchBaseHost`（pixibb 的 sexy 子域）
- 所有 URL（翻页 / 搜索 / 网关改写 / Google sitesearch）由「host + 路径/参数」拼装，业务代码**禁止**出现 `https://域名` 字面量
- 主域解析规则：显式 `role=primary` 优先，其次「首个非 m./www./mobile. 域」（与原 `googleSearchConfig` 规则一致）

### 3.3 id 路由 → 注册表路由

原先散落的 `site.id === 'xxx'` 分支全部改为读定义字段 + 查注册表：

| 原分支位置 | 现实现 | 定义字段 |
|-----------|--------|---------|
| `parseLinksForSite` 5 路 switch | `parsers.ts` → `LINK_PARSERS` | `linkParser` |
| `extractSearchImageCount` 3 路 switch | `parsers.ts` → `IMAGE_COUNT_RULES` | `imageCountRule` |
| `scanLinks` jrants/pixibb 特判 | `parsers.ts` → `SCAN_PARSERS` | `scan.recommended / scan.others` |
| jrants 翻页节流 | `service` 读定义 | `throttle` |
| `ID-buondua-*` 文件夹前缀 | `service` 读定义 | `folderTag` |
| 聚合搜索站点分组（阶段 1B） | view 由定义派生 | `channels` / `defaultChecked` / `label` / `uiOrder` |

### 3.4 模块分层

```
src/sites/
  schema.ts    定义类型（SiteDef）+ 运行期类型（GallerySiteConfig）
  defs/*.ts    每站一份纯数据定义 + index.ts 聚合（顺序敏感）
  engine.ts    定义 → 运行期对象编译 + 通用相册解析（容器/图片/页数/标题）
  parsers.ts   搜索页/推荐链接解析器、张数规则、扫描器注册表
  registry.ts  对外接口（GALLERY_SITES / matchGallerySite / siteById + 解析函数）
src/grabber/view-sites.ts   （阶段 1B）站点管理 UI
```

## 4. 数据流（保持不变）

```
grabber 页 → 消息(BD_*) → background(BuonduaService) → matchGallerySite(url)
  → engine 通用解析（容器/图片/页数/标题）
  → parsers 站内/Google 搜索页解析
  → 结果经 _FWD / BD_RESULT 推送回 grabber
  → 下载/打包：文件夹名 ID-{folderTag}-*，编号 001-N = 抓取顺序（既有约定不变）
```

## 5. 权限

- 多页图站全部走 background fetch 与页面内 fetch 降级（`BD_FETCH_HTML`），无静态 `content_scripts` 声明
- 权限仍依赖按需申请的 `optional_host_permissions: <all_urls>`
- **域名变化不涉及 manifest 改动**（这是本方案可行的前提），阶段 1B 的域名覆盖也不需要新增权限

## 7. 不在本阶段范围

- 不引入 DOM 解析（SW 无 DOMParser）：正文容器仍用「选择器字段 → 开标签正则」编译，行为与旧版等价
- 不迁移 imgbb 专用服务（图床语义不同，注册表后续以 `kind` 区分）
- 不改任何命名规则、页序、文件夹名（2026-10-06 命名约定保持不变）
- 不做远程站点目录（只做内置数据 + 用户手动覆盖，避免远程代码风险）
