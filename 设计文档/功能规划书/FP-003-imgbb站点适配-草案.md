# FP-003 站点适配：imgbb 图床（设计草案 v2）

- 状态：**DONE（2026-08-10 用户验收通过，功能完结）**
- 前置调研：浏览器 + curl 实测，含网络资料核对

## 一、调研结论（v2，含重大发现）

### 1. imgbb 内嵌数据（data-object JSON）— 核心宝藏

列表页每个 `.list-item` 带 `data-object`（URL 编码 JSON），**直接包含**：

| 字段 | 说明 |
|------|------|
| `image.url` | **原图 URL**（最大尺寸，如 2823×4250 / 13.8MB） |
| `medium.url` | 展示图（425×640 左右，列表页实际显示） |
| `thumb.url` | 缩略图（180×180） |
| `width` / `height` | **原图尺寸**（免加载） |
| `filename` / `name` | 原始文件名 |
| `url_viewer` | 详情页链接 |
| `user.username` | 上传者 |

→ **下载最大尺寸零额外请求**（原图 URL 直接在列表页 HTML 里）

### 2. 图片三档 URL 实测

| 档位 | URL 模式 | 实测尺寸 |
|------|---------|---------|
| 原图 | `i.ibb.co/{imageID}/{file}`（data-object image.url） | 2823×4250 / 13.8MB |
| 展示 | `i.ibb.co/{mediumID}/{file}`（列表页 img src） | 425×640 |
| 缩略 | `i.ibb.co/{thumbID}/{file}` | 180×180 |

（文件名加 `_t/_m/_l` 后缀均无效——新版 imgbb 无后缀变体）

### 3. 页面可访问性（关键修正）

| 页面 | curl 实测 | 结论 |
|------|----------|------|
| `{user}.imgbb.com/`（用户主页全部图片） | 重定向登录页 | **登录墙保护** |
| `{user}.imgbb.com/albums`（相册列表） | 正常 | **公开** ✓ |
| `ibb.co/album/{ID}`（相册详情） | 正常 | **公开** ✓ |
| `{user}.imgbb.com/following`（关注） | 正常 | **公开** ✓ |
| `i.ibb.co/...`（图片） | 200 + CORS `*` | 可下载可打包 ✓ |

→ **场景 2/3/4 全部后台 fetch 可行（公开页）；仅场景 1 用户主页受登录墙**

### 4. 分页/加载机制

- 用户主页：`?page=N&seek={游标}` 分页，**无 seek 直接访问被登录墙拦截**；页面内无限滚动正常（每批约 32 张）
- 相册列表：`/albums?page=N` 公开可跳页 ✓（curl 验证）
- 相册详情/关注页：静态渲染，无分页或少量分页

## 二、修正后的场景架构

| 子标签 | 数据通道 | 说明 |
|--------|---------|------|
| 1 用户主页 | **content script 注入**（会话内滚动解析）+ 后台 fetch 探测兜底 | 登录墙保护，需用户会话；支持分批/分页范围/编号范围 |
| 2 相册抓取 | **后台 fetch**（公开页） | 抓 `ibb.co/album/{ID}` 全部图片，原图 = data-object image.url |
| 3 相册分析 | **后台 fetch**（公开页） | `/albums?page=N` 分页，封面 + 名称，每批 30 |
| 4 关注墙 | **后台 fetch**（公开页） | `/following` + `/followers` → 各用户 `/albums` 检索相册，每批 30 用户 |

## 三、imgbb 解析器统一规则（imgbb-analyzer.ts）

- 列表项类型分流：`data-type="image"`（图片）/ `"album"`（相册）/ `"user"`（关注用户）
- 图片项：解析 `data-object` → 原图/展示/缩略 URL + 宽高 + 文件名
- 相册项：`data-id` / `data-name` + 封面图 + 链接
- 用户项：用户名 + 头像 + 链接
- 纯函数（HTML → 结构化数据），可单测

## 四、场景 1 细节（登录墙应对）

- **主通道**：用户打开 imgbb 页面后，注入 content script（现有 GRAB_PARSE_START 机制），滚动加载解析，data-object 原图直读
- **备选**：后台 fetch 探测（检测响应标题是否 "Sign in"），带浏览器 Cookie 的扩展 fetch 大概率可通过（实现时实测）
- 若两者都不可行：引导用户用「相册分析」+「相册抓取」组合（更组织化，且全部公开）
