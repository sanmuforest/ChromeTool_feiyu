# 2026-10-10-002 缩略图四级容错（错峰加载 + 延迟重试 + blob 兜底）

> 版本：**v0.2.17** ｜ 类型：Bug 修复（加载策略）+ 定性结论
> 触发：用户补充两条关键观察 —— ①新标签直接打开失败图**能正常显示**；②**网页端最终也加载出来了**

## 定性结论（本轮由用户观察拍板）

| 观察 | 推论 |
|------|------|
| 新标签直开该 URL 能显示 | 图片 URL 有效、图床正常 |
| **网页端（非插件）也破图，但稍后自行恢复** | 失败是**暂时性**的，与插件无关 |
| 我外部请求同一 URL 返回 `image/jpeg` | 排除链接失效 |

→ **根因判定：图床（`i0.wp.com` WordPress Photon）对突发并发的限流/暂时性拒绝**。相册页几十张图同时请求 → 部分被拒或超时 → 稍后重试即成功。

因此这不是网站故障、不是链接失效、也不是 Referer 防盗链（v0.2.15 的假设已由实测排除）。

## 改动（`image-grab-view.ts`）—— 从"失败即兜底"升级为四级容错链

| 级 | 措施 | 目的 |
|----|------|------|
| ① | **错开加载**：网格缩略图按 80ms 间隔依次赋值 `src`（最多错开 2s） | **从源头降低突发并发**，不触发图床限流（最关键的一级） |
| ② | **延迟重试**：失败后 1.2s / 2.4s 各重试一次，URL 附 `retry=N&t=<ts>` 强制重新请求 | 救"暂时性失败"（本次现象的主要成因） |
| ③ | **blob 兜底**：仍失败则经 `GRAB_FETCH_IMAGE` 取字节转 blob 显示，并记录 `bytes` 与 `head` | 兜住真正取不到、或加载路径失败的情况 |
| ④ | **标记失败**：以上都不行才标「加载失败」+ 限流日志 | 明确状态，不再只是破图 |

角标会随状态变化：`尺寸…` → `重试中 1/2…` → `兜底加载中…` → `加载失败`。

**未触碰**：解析、去重、筛选、选择、下载、打包、命名；下载仍走原图 URL（`downloadUrlOf`），重试附带的 query 参数只影响显示。

## 实测结果（2026-10-10，v0.2.17）

用户复测反馈：**大部分缩略图加载成功**，仅**很少几张**走完重试与兜底后显示「加载失败」。

结论：四级容错链达到设计目标 —— 错峰加载消除了突发并发（不再触发图床限流），暂时性失败被重试救回；剩余个别失败属"当前网络下持续取不到"，已在本轮达成可接受的收敛点（相对之下，站点网页端本身仍有成片破图）。

## 说明与权衡

- **错峰加载的代价**：大相册（如 100 张）缩略图会分批出现，比原来"瞬间铺满"慢；换来的是不触发图床限流、破图大幅减少。若你希望更快，可把 80ms 调小（`staggerIndex++ * 80`）
- **重试参数的权衡**：给重试 URL 附加 `retry/t` 查询参数以绕过浏览器对失败结果的缓存。绝大多数 CDN 忽略未知参数；若将来遇到**签名 URL** 的站点（参数参与校验），需要改为"仅置空再赋值"的重试方式
- **网页端破图仍会有**：那是站点自身一次请求几十张图的固有行为，插件无法改变；插件侧已通过错峰把自身触发的并发降到最低
