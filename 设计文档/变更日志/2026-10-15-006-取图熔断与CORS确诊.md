# 2026-10-15-006 取图熔断（解决大相册卡死）+ 取图失败确诊为 CORS

> 版本：**v0.2.40** ｜ 类型：性能保护（熔断）+ 诊断结论
> 触发：用户 v0.2.39 日志（含上一轮加的 `srcError` 诊断字段）

## 一、确诊：取图失败是 **CORS 拦截**，不是 403

```
GRAB_FETCH_IMAGE 源页注入失败，降级 background {
  srcError: "页面内 fetch 失败：TypeError: Failed to fetch",
  url: "https://img.xchina.io/photos/6ab82e0dab417/00087.jpg"
}
```

`TypeError: Failed to fetch` 是浏览器在**跨域读取响应被 CORS 阻止**时的标准报错（若是 HTTP 状态问题会显示 `HTTP 403`）。

**结论**：`img.xchina.io` 不返回 CORS 响应头 → **页面内 fetch 这条路读不到任何数据**，与 Cookie / Referer 是否正确无关。

结合已知信息，该图床的三层防护：

| 通道 | 结果 | 原因 |
|------|------|------|
| 扩展页 `<img>` 直接加载 | 失败 | 服务器拒绝（Referer/CF 校验） |
| 页面内 fetch（`world:'MAIN'`） | **失败** | **CORS 阻止读取响应** |
| background fetch | 403 | 无站点 Cookie |

→ 属**通道问题**，不是配置问题。需换思路（见第五节）。

## 三、卡死的根因

720 张图，每张失败后走完「重试 2 次（带时间戳）→ blob 兜底（源页注入 1 次往返）→ 后台 fetch」≈ **4 次失败请求/张** → 约 **3000 次请求** → 页面拖死。

## 四、改动：按图床 host 的失败熔断

`src/grabber/image-grab-view.ts`：

```ts
const FAIL_CIRCUIT_LIMIT = 8
// 同一 host 连续失败达 8 次 → 后续图直接标记「加载失败」，不再重试与兜底
if (isCircuitOpen(img.url)) { markFailed(); return }
```

- `load` 成功时清除该 host 的失败计数（避免偶发失败累积误触发）
- 正常站点不会触发（需同一图床连续失败 8 次）
- 效果：8se.me 这类「取图通道全不可用」的站，从第 9 张起快速失败，不再产生数千次请求

## 五、下一步需要用户实验（决定取图方案）

熔断只解决「卡死」，**图片仍然取不到**。要真正能看图/下载，需要确定还有哪条通道可用：

| 实验 | 做法 | 若成功说明 |
|------|------|-----------|
| **① 浏览器原生下载** | 选中 1~2 张 → 点「**下载选中**」 | 走的是 `chrome.downloads.download`（浏览器一级请求，不受 CORS 限制、带正常 Cookie）→ 可把下载路径整体切到它 |
| ② 相册真实张数 | 打开该相册数一下总数 | 若远小于 720 → 说明翻页存在重复计数问题（需再查） |

若 ① 也不行，后续只能考虑：`declarativeNetRequest` 给图片请求注入 Referer（需新增权限，并需实验验证能否过 CF），或接受该站「可列出、不可下载」并明确标注。
