# 2026-11-06-008 v0.2.66 参数回滚 + 打包失败集中重试

> 版本：**v0.2.67** ｜ 类型：参数修正 + 打包流程改进
> 触发：用户实测 v0.2.66 后反馈「依然非常慢」，提供 97 条日志

## 一、v0.2.66 实测结果：**参数调错了，反而更差**

| 版本 | 参数 | 抓取 | 打包 | 耗时 |
|------|------|------|------|------|
| v0.2.65 | 超时 40s / 并发 12 / 重试 3 | 69 | **59/69（85%）** | 3 分 34 秒 |
| **v0.2.66** | 超时 **12s** / 并发 **3** / 重试 **1** | 92 | **52/92（57%）** ❌ | **6 分 15 秒** ❌ |

日志里 `AbortError` 出现 **40+ 次**。

## 二、错在哪

v0.2.66 的假设是「imgbb 对并发敏感，所以要低并发 + 短超时快速失败」。实测证明**后半句完全错误**：

- imgbb 单张实测就要 **1~10 秒**，并发下更慢
- 把超时压到 **12 秒** = **自己把还在传输的请求掐断**
- 结果：`AbortError` 暴增、成功数从 59 掉到 52、耗时从 3.5 分钟涨到 6.25 分钟

**正确认识：imgbb 的问题不是"请求太多"，而是"每次请求本身就慢"。** 压超时等于自杀。

## 三、改动

### 1. 参数回滚与重新取值（`src/lib/downloader.ts`）

| 参数 | v0.2.66（错） | **v0.2.67（现）** | 依据 |
|------|--------------|------------------|------|
| 超时 | 12 秒 | **30 秒** | 覆盖实测最慢 10.5 秒，并给并发留余量 |
| 并发 | 3 | **8** | 折中：高于 3（吞吐不足）低于 12（实测一半超时） |
| 重试 | 1 次 | **2 次** | 与超时配套，避免单次抖动即失败 |
| 退避 | 300ms | **1000ms** | 给服务端喘息 |

### 2. 新增诊断日志：区分「超时掐断」与「其他中断」

```ts
if (/abort/i.test(lastErr.message)) {
  logger.warn('download', '取字节被中断', { host, elapsedMs, timeoutMs,
    likelyTimeout: elapsedMs >= timeoutMs - 800 })
}
```

依据：这两种中断的优化方向**完全相反**（前者该加长超时，后者要查 SW 生命周期），不能靠猜。下次日志里若 `likelyTimeout: true`，说明超时仍不够；若 `false`，说明是 SW/资源中断。

### 3. 打包改两阶段：失败集中重试（`src/grabber/image-grab-view.ts`）

原流程：每张图**原地**重试（在 `fetchImageBytes` 内部），失败即放弃。
问题：imgbb 的失败多为**瞬时**（503 / 连接重置 / 传输中断），原地重试受限于同一时刻的服务端状态。

新流程：

```
阶段 1：并发 worker 跑全部（失败项收集到 failedItems，不阻断其他图）
阶段 2：把 failedItems **顺序**重试 2 轮（低并发，避免再次触发限流）
```

- 抽出 `fetchOneBlob(item)` 供两个阶段复用（含 blobCache 命中、imgbb 通道、直连回退）
- 阶段 2 每张成功即写入 ZIP 并计入 `okCount`
- 结束后打一条「打包失败项（集中重试后仍失败）」记录剩余数量
