# 2026-11-06-002 imgbb 错误图：显示改走 blob 取字节

> 版本：**v0.2.61** ｜ 类型：显示通道缺陷修复
> 触发：用户反馈「抓取页有一大把蓝色 'imgbb.com service unavailable' 失败图，但打包下载了 66 张，比抓取页显示的还多」

## 一、现象与日志解读

截图：抓取页网格里大量格子显示蓝底 `imgbb.com service unavailable` 占位图，且每格**仍标注真实尺寸**（2048×1536 等）。

日志（v0.2.60）：

```
相册全量抓取完成 { count: 77, pages: 2, name: "Baocnao521" }   ← 77 张全部抓到
打包下载完成     { ok: 66, total: 77 }                          ← 打包成功 66 张
```

**关键判断**：
- 抓取**没有漏**（77 = 相册实际张数）
- 蓝色错误图是**显示问题**，不是抓取问题
- 「打包比显示多」正好证明：打包走 background fetch 能拿到字节，而网格走 `<img>` 拿不到

## 二、根因：200 的错误图，无 error 事件

`i.ibb.co` 对扩展页的 `<img>` 请求返回 **HTTP 200 + 一张 "service unavailable" 错误图**，而不是 4xx。

后果：浏览器认为**加载成功** → **不触发 `error` 事件** → `image-grab-view.ts` 里精心搭的五级容错（错峰 → 延迟重试 → blob 兜底 → 标记失败 → 手动重试）**全部被跳过**，直接显示错误图。

### 已排除的因素（实测）

对同一张 `https://i.ibb.co/pm5rPtD/HIXe-MCrbk-AAJoq-V.jpg` 分别测试：

```
无 Referer（≈ no-referrer）      → HTTP 200  102612 bytes  image/jpeg  1024x768
chrome-extension:// Referer      → HTTP 200  102612 bytes  image/jpeg  1024x768
imgbb 站内 Referer                → HTTP 200  102612 bytes  image/jpeg  1024x768
i.ibb.co 同源 Referer             → HTTP 200  102612 bytes  image/jpeg  1024x768
```

- **没有 Referer 防盗链**（`chrome-extension://` 也放行）
- **不是 180×180 降级**（1024×768 / 102KB，是真图）
- → 结论：错误图是 imgbb 对**扩展页高频 `<img>` 请求**的软限制表现
- → 且 **background fetch 是可靠的**（四种 Referer 都拿到真图）

## 三、改动（`src/grabber/image-grab-view.ts`）

| # | 改动 | 说明 |
|---|------|------|
| 1 | 新增 `IMGBB_IMG_RE` | 匹配 `i.ibb.co` 与 `*.imgbb.com` 的图片 URL |
| 2 | `ensureThumbObserver` 的按需加载分支 | 该域图片**跳过 `<img>`**，直接调 `recoverThumb()` → background 取字节 → `URL.createObjectURL(blob)` 显示 |

**为什么用 blob 而不是别的办法**：`<img>` 无法设置 Referer、无法读响应体，而错误图是 200 无法判定，唯一可靠路径就是自己取字节。

复用已有的 `recoverThumb()`（v0.2.41 引入），它内部走 `GRAB_FETCH_IMAGE` → 源页注入（对 `i.ibb.co` 跨子域会 CORS 失败）→ 降级 background `fetchImageBytes`（**带 429/503 退避**，v0.2.60）。

## 六、附带说明：11 张 503 是另一回事

```
GRAB_FETCH_IMAGE 抓取失败 { error: "Error: HTTP 503" }
```

这是 **imgbb 服务端的临时不可用**（503），不是限流也不是代码问题。v0.2.60 已对它做 3 次退避重试（800/1600/3200ms），全部失败才会报错。

**建议**：过一段时间对失败的 11 张重新打包即可（imgbb 通常几分钟内恢复）。若长期失败，可考虑增加重试次数或延长退避，但那属于策略调整，未在本次实施。
