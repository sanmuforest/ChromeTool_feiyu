# 2026-10-17-017 抓取网格缩略图与原图分离（全屏卡顿修复）

> 版本：**v0.2.51** ｜ 类型：性能修复
> 触发：用户反馈「全屏窗口抓取时同时加载太多图导致卡顿，小窗口明显流畅」

## 一、根因

1. 多页图站解析出的图片对象（`parseGalleryImages`）**没有 `thumbUrl`**，网格 `displayUrlOf()` 回退到 `img.url`。
2. `img.url` 经 `imageThumbFix` 处理，已经是**原图**（如 xchina 的 `000NN.jpg`），不是 600px 预览。
3. 网格列宽固定 150px，全屏一屏可见/预加载 40–60 张，小窗口只有 10–15 张；`rootMargin: 300px` 又在视口外多预载一圈。
4. 结果：全屏时同一时刻解码几十张 1000px+ 原图，解码内存与 GPU 纹理峰值可达数百 MB；小窗口压力小，所以流畅。

## 二、改动

### 1. `src/lib/types.ts`

`BuonduaImage` 增加可选 `thumbUrl?: string`（仅展示用）。

### 2. `src/sites/engine.ts`

`parseGalleryImages` 在 `imageUrlClean`（含 `imageThumbFix` / `imageQueryFix`）改写 URL 时：

```ts
const finalUrl = clean ? clean(url) : url
const thumbUrl = finalUrl !== url ? url : undefined
return { url: finalUrl, filename, thumbUrl }
```

- `url` 仍是原图（下载/打包用）
- `thumbUrl` 是改写前的预览 URL（xchina/se8 的 `_600x0.webp`、phimvuspot 的 `?w=640`）
- 没有改写规则的站点 `thumbUrl` 为空，行为不变

### 3. `src/grabber/view-buondua.ts`

`toGrabbed()` 传递 `thumbUrl: img.thumbUrl`；`downloadUrl` 仍为 `img.url`（原图）。

### 4. `src/grabber/image-grab-view.ts`

`rootMargin` 300px → 150px，减少全屏时视口外一圈的预加载量。

## 三、下载安全（避免 180×180 小预览的历史问题）

下载链路不读 `thumbUrl`：

- `downloadUrlOf(img) = img.downloadUrl ?? img.url` → 原图
- 打包 `items` 由 `downloadUrlOf` 生成 → 原图
- 双击预览 `previewImg.src = downloadUrlOf(img)` → 原图
- `thumbUrl` 只出现在网格 `displayUrlOf()` 中

## 四、验证

- `npm run typecheck`：通过
- `npm run build`：通过，当前版本 **v0.2.51**

## 五、用户实测清单

1. `chrome://extensions` 刷新扩展（必须）
2. 全屏抓同一个相册，观察网格加载是否明显更流畅、滚动是否少卡顿
3. **下载一张图，确认尺寸/文件名是原图**（不是 `_600x0.webp` 预览、不是很小的小图）
4. 双击预览，确认显示的是原图
5. 若某站缩略图大量失败（网格显示「兜底加载中…」或失败标记），贴日志——可能是该站的预览 URL 规则与 `imageThumbFix` 不匹配，需要单独看

## 六、已知限制

- 只有配置了 `imageThumbFix` / `imageQueryFix` 的站点会生成 `thumbUrl`；其余站点行为不变（仍是原图直显）。
- xchina 图床对扩展页加载可能 403，缩略图失败后仍会走 blob 兜底（用原图字节），这部分并发压力没有在本轮处理；若实测仍卡，下一步给兜底加并发上限。
