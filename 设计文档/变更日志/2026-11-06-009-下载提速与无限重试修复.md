# 2026-11-06-009 文件夹下载提速 + 修复无限重试

> 版本：**v0.2.68** ｜ 类型：性能修复 + 严重缺陷修复
> 触发：用户指出「当前 imgbb 文件夹下载优于打包下载，需要对文件夹下载优化提高效率，并优化自动重试防断联」

## 一、从日志算出来的真相：下载实际是「串行」的

v0.2.67 用户实测（92 张的相册，走「下载」而非打包）：

```
下载任务完成 { done: 92, failed: 0, total: 92, totalMs: 350171, avgMsPerItem: 3806, concurrency: 12 }
```

验算：

```
avgMsPerItem 3806ms × 92 张 = 350 秒 ≈ totalMs 350171ms
```

**如果是真的 12 并发，应该只要约 29 秒。** 说明**整个下载几乎在串行执行**，「concurrency: 12」只是配置值，没真正生效。

## 二、串行的原因：host 限速把所有请求排成了队

v0.2.60 为「防 429 限流」引入了按 host 生效的最小间隔：

```ts
const HOST_THROTTLE_GAP_MS = 500   // 一旦该 host 出现 429/503，之后每次请求都要等 500ms
```

imgbb 一旦出现 503，此后**每一次请求都要排队等 500ms** → 整个 host 串行化。

**但关键事实**：日志里 imgbb 的失败形态**全是超时**，不是 429：

```
取字节被中断 { elapsedMs: 30000, likelyTimeout: true, timeoutMs: 30000 }
取字节被中断 { elapsedMs: 61025, likelyTimeout: true }
```

**用串行化对付超时问题，既治不了超时，又把并发彻底废了。**

## 三、顺带发现的严重 bug：下载中断会**无限重试**

```ts
this.active.set(downloadId, { ..., attempts: 0, ... })        // 每次都重置为 0
} else if (active.attempts < MAX_RETRY) {                      // 0 < N 永远成立
  this.queue.push({ jobId, item, enqueuedAt })                 // 重新入队，但不带 attempts
}
```

重试项入队时**没有携带重试次数**，重建的 `active.attempts` 又是 0 → 条件永远成立 → **无限重试**。

这会让任务永不收敛（一直重试同一张图），也是「效率低 / 防断联差」的隐藏原因。

## 四、改动（均在 `src/lib/downloader.ts`）

| # | 改动 | 说明 |
|---|------|------|
| 1 | 新增 `IMGBB_HOST_RE` 常量 | 统一 imgbb 主机判定（同时供 `HOST_POLICIES` 使用，避免重复定义） |
| 2 | `noteHostResult()`：imgbb **不再启用 host 串行化** | 它的失败是超时不是限流；并发改由 `jobConcurrency`（策略值 8）控制 |
| 3 | 队列项增加 `attempt?` 字段 | 中断重试时携带次数 |
| 4 | `handleChanged()` 重试入队带 `attempt: active.attempts + 1` | 修复无限重试 |
| 5 | `startOne()` 增加 `attempt` 参数并回填 `active.attempts` | 重试次数真正生效 |
| 6 | `MAX_RETRY` 1 → **2** | 防断联：imgbb 常在传输中途被中断，多一次重试显著减少永久失败 |

## 五、预期效果

| 指标 | 改动前（v0.2.67） | 改动后（v0.2.68） |
|------|------------------|------------------|
| 实际并发 | ≈ 串行（1） | **8**（jobConcurrency） |
| 92 张总耗时 | 350 秒 | 预期 **60～120 秒** |
| 下载中断重试 | 无限（bug） | **最多 2 次**（共 3 次尝试） |
| imgbb host 间隔 | 500ms 串行 | 不启用 |

- **打包路径**这次未改动（仍走 v0.2.67 的两阶段重试）
