# 2026-11-06-004 下载队列并发失效（imgbb 四个症状的根因）

> 版本：**v0.2.63** ｜ 类型：**严重缺陷修复**（并发控制 + 资源泄漏）
> 触发：用户要求「对 imgbb 做一次彻底诊断」，并列出四个症状

## 一、四个症状的完整归因

| 症状 | 真实原因 |
|------|----------|
| **文件夹下载完成第一张后就卡死** | **并发计数完全失效** → 77 个 `chrome.downloads.download` 一次性全部发起 |
| **打包固定缺失约 10%** | 全部并发的 imgbb 请求触发限流 → 固定那批返回 503 |
| **前半段下载快、之后越来越慢** | 并发爆炸 + 每张图的 base64 `data:` URL 累积 + object URL 泄漏 |
| **抓图显示不全** | 取字节请求同样全部并发，排队与限流拖慢显示 |

四个症状是**同一个根因**的不同表现，不是四个独立 bug。

## 二、根因：`pendingFetches` 用了 jobId 作为 Set 元素

```ts
// 修复前
private pendingFetches = new Set<number>() // 注释写「jobId → 正在 fetch（占并发槽）」

private pump(): void {
  while (this.active.size + this.pendingFetches.size < this.maxConcurrent && this.queue.length > 0) {
    const next = this.queue.shift()
    this.pendingFetches.add(next.jobId)          // ← 加的是 **jobId**
    void this.startOne(...).finally(() => {
      this.pendingFetches.delete(next.jobId)     // ← 删的也是 jobId
```

**同一 job 的所有文件共享一个 jobId**（77 个文件 → 1 个 jobId）：
- `Set` 去重后 `size` **恒为 1**
- `active.size + pendingFetches.size` 几乎永远小于并发上限（12）
- → **`pump()` 会把整个队列一次性派发完**
- → 77 个下载同时发起、77 个 imgbb fetch 同时发起

这也解释了「第一张完成后卡死」：第一张很快完成（图片小、CDN 快），与此同时剩下 76 个已经在浏览器里同时排队下载。

### 连带缺陷 2：`fetchControllers` 同样按 jobId 存

```ts
private fetchControllers = new Map<number, AbortController>()  // jobId → controller
this.fetchControllers.set(job.id, controller)                  // 每项都覆盖同一个 key
```

同一 job 的后续项会**覆盖**前面的 controller → 取消任务时只能中断最后一项，其余无法 abort。

### 连带缺陷 3：object URL 泄漏

`recoverThumb()` 每次调用都新建 `URL.createObjectURL(blob)` 且**从不 revoke**。列表重建（筛选/排序/刷新）时持续累积 → 越用越卡。

## 三、改动（`src/lib/downloader.ts` + `src/grabber/image-grab-view.ts`）

### downloader.ts

| # | 改动 | 说明 |
|---|------|------|
| 1 | `pendingFetches: Set<number>` → **`pendingByJob: Map<number, number>`** | 按 job 记录「正在 fetch 的项数」，并发计数恢复正确 |
| 2 | 新增 `pendingFetchTotal()` | 跨 job 汇总 fetch 中项数，参与并发槽计算 |
| 3 | 完成态判断改用 `pendingByJob.get(job.id)` | 只有该 job 自身还有 fetch 中的项时才算未完成 |
| 4 | `fetchControllers: Map<jobId, ctrl>` → **`Map<controller, jobId>`** | 每项独立 controller，取消时按 jobId 遍历中断 |
| 5 | `startOne` 的 controller 清理移入 `finally` | 避免提前 return 时残留 |

### image-grab-view.ts

| # | 改动 | 说明 |
|---|------|------|
| 6 | `blobCache: Map<url, Blob>` → **`Map<url, { blob, objectUrl }>`** | 每个 URL **只创建一次** object URL 并复用，不再每次新建导致泄漏 |
| 7 | 打包取缓存改为 `blobCache.get(url)?.blob` | 适配新结构 |

## 四、预期效果

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| 并发下载数 | 全部（77） | **≤ 12**（按设置） |
| imgbb 限流 503 | 固定约 10% | 显著减少（并发受控） |
| 下载完成率 | 可能卡死/中断 | 应可完整走完 |
| object URL 累积 | 无上限 | 每图 1 个、复用 |
| 打包速度 | 4.5 分钟 | 缓存命中时数十秒 |

## 五、验证

- `npm run typecheck`：EXIT=0
- `npm run build`：通过（v0.2.63）
- 逻辑审阅：
  - `pump()` 的 while 条件现在能正确反映「在途数量」，并发槽生效
  - `pendingByJob` 归零后删除 key，避免 Map 无限增长
  - 取消路径遍历 `fetchControllers` 中断该 job 全部在途 fetch
  - 非 imgbb 站点不受影响（只改了并发调度与缓存结构）

## 六、用户实测清单

1. **刷新扩展**（改了 background 与 grabber，必须刷新）
2. 抓一个 imgbb 相册（如 77 张的 `https://ibb.co/album/f4npz4`）
3. **测试「下载选中」**：应平稳推进、不再第一张后卡死；日志「下载任务完成」里的 `concurrency` 应为 12
4. **测试「打包」**：先滚动让图片显示，再打包，应在数十秒内完成
5. 观察 `ok/total`：缺失比例应明显低于原来的 10%

## 七、诊断中确认但本次未改的点

| 点 | 现状 | 说明 |
|----|------|------|
| `startOne` 对 imgbb 仍先试源页注入 | 每张白跑一次 CORS 失败 | v0.2.62 只改了打包路径（`GRAB_FETCH_IMAGE`），下载路径未改；同一图床这步 100% 失败，可跳过但要另行确认 |
| imgbb 用 base64 `data:` URL 交给 downloads | 每张 ~133KB 字符串 | 单张可接受，但 77 张会占用较多内存；可考虑改 blob URL |
| 503 重试仍为 3 次 / 800-1600-3200ms | 未动 | 影响成功率与耗时，需用户决策 |

**先验证并发修复的效果**，再决定是否继续动这三项 —— 避免一次改太多导致无法归因。
