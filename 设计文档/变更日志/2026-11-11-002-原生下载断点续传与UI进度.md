# 2026-11-11-002 原生下载断点续传 + 分批节流 + UI 进度

> 版本：**v0.2.73** ｜ 类型：功能增强（在 v0.2.72 原生下载基础上）
> 触发：用户实测 v0.2.72 的浏览器原生下载「只有 175 张成功下载，该相册有 500+」

## 一、实测数据对比

| 通道 | 成功后触发限流 | 说明 |
|------|---------------|------|
| fetch（v0.2.71 及之前） | **22 张** | 完全不可用 |
| `chrome.downloads`（v0.2.72） | **175 张** | 宽容约 8 倍，但仍有限 |

结论：`chrome.downloads` 是当前唯一能过 Cloudflare 的通道，但**单次跑不完 500+ 张**。
所以问题从「通道不可用」变成「一回合跑不完」—— 需要**可中断、可续跑**。

## 二、改动（`src/grabber/image-grab-view.ts`）

### 1. 断点续传

```ts
const DL_RESUME_KEY = 'grab_native_done_urls'   // { [文件夹名]: string[] }
```

- `loadNativeDone(folder)`：读取该文件夹已成功落盘的 URL 集合
- 每成功一张就把 URL 加入集合；每 10 张 `saveNativeDone()` 落盘一次
- **下次点打包时只下载缺的部分**，不再从 0 重跑到 175

设计要点：
- 按**文件夹名**分组 —— 不同相册互不干扰
- 存 `chrome.storage.local`（非 session），关掉浏览器再开仍有效
- 存储失败不影响本次下载（只是下次会重下）

### 2. 分批 + 节流

| 参数 | 值 | 依据 |
|------|-----|------|
| `NATIVE_GAP_MS` | **250ms** | v0.2.72 用 60ms，175 张就触发；放大约 4 倍 |
| `NATIVE_BATCH_SIZE` | **100 张** | 一批 100 张，低于 175 的触发点 |
| `NATIVE_BATCH_PAUSE_MS` | **30 秒** | 批次间暂停，让频率/流量计数降温 |

### 3. UI 实时进度（本次重点）

原生下载是逐个串行跑，一张 250ms 间隔，500 张要几分钟 —— 必须有实时反馈。

**每张下载后刷新**：

```
原生下载 175/522（34%） 本次成功 175 跳过 0 失败 0 累计 175/522 剩余 347
```

**每批暂停时**：

```
已完成 100 张（跳过 0 张已下），暂停 30 秒避开限流…
```

**结束时**：

```
打包完成：ZIP 内 0 张；本次原生下载 175 张；累计 175/522，再点一次「打包」可继续补齐
```

进度条同步（`dlFill` 宽度按「已处理 / 总数」推进）。

## 四、用户实测清单

1. **刷新扩展**（确认 v0.2.73）
2. 抓同一个 522 张的相册 → 打包
3. 观察 UI：
   - 进度文案应是 `原生下载 X/522（Y%）本次成功 N 跳过 M 失败 K 累计 C/522 剩余 R`
   - 每 100 张会看到「暂停 30 秒避开限流…」
4. **分几次跑**：
   - 第一次跑到某处停住/失败
   - 直接再点一次「打包」→ 应看到 `跳过 N 张已下`，本次只下缺的
   - 重复直到提示 `已全部完成`
5. 最终校验：下载目录里的图片数量应接近 522

## 五、参数是否要调，取决于本次结果

| 观察到的现象 | 调整方向 |
|--------------|----------|
| 每次仍卡在 175 左右 | 说明是「累计流量/次数」限流而非频率，需要拉长批次间隔（如 2 分钟）或把批大小降到 50 |
| 卡在 175 但分批后有改善 | 说明频率控制有效，可微调 `NATIVE_GAP_MS` |
| 换代理节点后不再限流 | 说明是 IP 问题，参数可调回激进值（60ms / 200 张一批） |

## 六、已知限制

- 这批图**不在 ZIP 里**（`chrome.downloads` 不返回字节）
- 会产生大量单条下载记录（522 条）

- 断点记录按文件夹名存，**改名相册会丢失续传进度**
