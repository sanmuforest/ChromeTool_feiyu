# 2026-10-10-009 修复：抓取触发站点 429 限流（页间节流 + 退避）

> 版本：**v0.2.24** ｜ 类型：回归修复（本人引入）+ 通用健壮性
> 触发：用户抓取 knit.bid 报错 `请求失败：Error: Error: HTTP 429`

## 根因（本次由我引入）

v0.2.22 为 knit.bid 启用了 `followPagesUntilEmpty`，把抓取上限提到 **40 页**；而 `fetchAlbumAllPages` 的翻页循环**没有任何页间间隔**：

```ts
for (const pageUrl of all) {
  const html = await getHtml(pageUrl)   // ← 连发请求，无间隔
  ...
}
```

→ 对一个页面连发几十个请求 → **站点返回 429（Too Many Requests）**。属于「顺序翻页能力」引入时没有配套限流。

## 改动

| # | 改动 | 说明 |
|---|------|------|
| 1 | `fetchAlbumAllPages` 支持站点 `throttle` | 页间延迟与**站内搜索共用同一配置**（`fromPage` / `delayMs`），无需新字段 |
| 2 | `defs/knitbid.ts` 配 `throttle: { fromPage: 2, delayMs: 1200 }` | 第 2 页起每页等待 1.2s |
| 3 | `fetchOnce` 对 **429 / 503** 退避 | 命中即先 `sleep(2500)` 再抛错，交由既有 `FETCH_ATTEMPTS = 2` 的重试避开限流窗口；日志记录 `HTTP 429 被限流，等待 2500ms 后重试` |
| 4 | **复用第 1 页内容**（顺带优化） | 循环原先从第 1 页开始，而 `firstHtml` 已经抓过第 1 页 → **每轮抓取都重复请求一次首页**；现改为 `pageIndex === 0` 直接复用，少发一次请求 |
| 5 | 可读错误提示 | `humanizeFetchError` 增加 429 映射（`被站点限流（429，请求过于频繁）：请等待几分钟后再试`）；`BD_FETCH_ALBUM` 的失败文案改用该映射（此前界面直接显示 `Error: Error: HTTP 429` 这类原始串） |

## 验证

- `npm run typecheck`：EXIT=0
- `npm run build`：通过，**当前版本 v0.2.24**

## 用户实测清单

1. 重载 `dist/`（确认徽标 **v0.2.24**）
2. **若刚才已触发站点限流，请等待几分钟再测**（站点侧限流窗口通常几分钟到十几分钟）
3. 抓取 `https://xx.knit.bid/ja/article/29937/`：
   - 预期日志出现 `启用顺序翻页（分页总数不可测）{ detected: 2, cap: 40 }`
   - 翻页过程中每页之间有约 1.2s 间隔（整体变慢属预期）
   - 若中途命中 429，日志会出现 `HTTP 429 被限流，等待 2500ms 后重试`，且通常会自行恢复
4. 若最终仍失败，界面提示应为「**被站点限流（429，请求过于频繁）：请等待几分钟后再试**」，而不是原始 `Error: Error: HTTP 429`
5. 回归：其它站点抓取应更快一点（少了一次首页重复请求）

## 说明

- **教训**：新增「顺序翻页」这类会放大请求量的能力时，必须同时给出限流配套 —— 本次是先加了能力、后补的节流（用户实测才发现）
- 页间延迟可按需调整：`defs/knitbid.ts` 的 `throttle.delayMs`；若该站限流更严可提到 2000ms
- `throttle` 现在作用于**两条路径**：站内搜索翻页（原本就有）与相册顺序翻页（本次新增）
