# 2026-11-07-002 修复 imgbb 下载进度与角标不更新（路由靠文件夹名猜）

> 版本：**v0.2.70** ｜ 类型：严重缺陷修复（进度显示链断）
> 触发：用户反馈「版本对、下载内容完整正确，但进度条和角标都没显示正确」

## 一、根因：进度派发靠 `folderName` 里是否含「相册」二字

`src/grabber/view-adapters.ts` 的 `routeDownloadJob()`：

```ts
function routeDownloadJob(job: DownloadJob): void {
  if (job.folderName.includes('用户主页')) {
    homeGrabView.setDownloadJob(job)
  } else if (job.folderName.includes('相册')) {   // ← 靠名字猜
    albumGrabView.setDownloadJob(job)
  }
}
```

而 imgbb 相册的文件夹名来自站点/用户，实测为：

```
"folderName": "白衬衫"
"folderName": "JK"
"folderName": "JVID Caroline - 卡洛琳《乳夹の调教》"
```

**没有一个包含「相册」二字** → 两个分支都不命中 → **进度从不派发给任何视图**。

后果正好吻合用户描述：
- **下载内容完整正确** —— 下载队列在 background 跑，与这个路由无关
- **进度条不动** —— `setDownloadJob` 从未被调用
- **角标不显示** —— 角标状态依赖 `job.doneUrls` / `job.failedItems`，`job` 一直是 null

## 二、改动

`routeDownloadJob()` 改为**同时推给两个视图**：

```ts
homeGrabView.setDownloadJob(job)
albumGrabView.setDownloadJob(job)
```

依据：
- 两个视图各自持有独立的 `job` 状态，未激活的那个只是不可见，同步状态无副作用
- 相比继续猜文件夹名，直接派发不会漏

**对比参考**：`view-buondua.ts` 的 `routeDownload()` 用的是**实际文件夹名精确匹配**
（`job.folderName === lastAlbumFolder` / `batchFolders` 遍历）—— 那种做法是可靠的，不需要改。
本次只修 `view-adapters.ts`。

## 三、验证

- `npm run typecheck`：EXIT=0
- 链路核对：`GRAB_DOWNLOAD_PROGRESS` → `adaptersView.onDownloadProgress` → `routeDownloadJob` → `setDownloadJob` → `renderDownload` → `updateDownloadBadges`
- `npm run build`：通过（v0.2.70）

## 四、用户实测清单

1. **刷新扩展**（确认 v0.2.70）
2. 抓一个 imgbb 相册 → 「下载选中」
3. 预期：
   - 进度条显示 `下载中 X/N（Y%）成功 A 失败 B 进行中 C`，且 A+B+C = N
   - 缩略图右下角：成功的出现绿色 **✓**，失败的红色 **!**
   - 点红色 ! 可单张重试

## 五、教训

**用「业务名称包含某关键字」来判断路由是不可靠的** —— 名称由站点/用户决定，无法保证含任何特定词。
应改用**显式标识**（来源视图 id、jobs 的归属关系）或**直接广播**。
