# 2026-11-11-007 修复 SPA 翻页卡死（后台标签页节流 → 改源标签页批量导航）

> 版本：**v0.2.79** ｜ 类型：严重缺陷修复（循环几次后卡住）
> 触发：用户反馈「效果并不理想 循环几次之后卡住了」

## 一、根因：后台标签页被浏览器节流

v0.2.77/78 用 `chrome.tabs.create({ active: false })` 开临时标签页逐页抓：

```ts
const tab = await chrome.tabs.create({ url, active: false })
while (Date.now() < deadline) {
  const t = await chrome.tabs.get(tabId)
  if (t.status === 'complete') break   // ← 后台标签页迟迟不 complete
  await new Promise((r) => setTimeout(r, 300))
}
```

**Chrome 会节流非激活标签页**（限制定时器、降低渲染优先级）。表现：

- `status: 'complete'` 迟迟不触发 → 每页都要等满 25 秒超时
- 超时后仍去读 DOM，但页面可能还没渲染完 → 读到 0 张
- 逐页累积 → 几页之后体感就是「卡住」

## 二、改动（3 处，架构调整）

### 1. `dom-fetch.ts`：`extractPagesByTabNavigation`

用**源标签页**（激活态，不会被节流）替代临时标签页：

```ts
extractPagesByTabNavigation(tabId, urls, {
  selector, hosts,
  renderWaitMs: 600,
  timeoutMs: 15000,
  stopAfterEmptyPages: 3,
  onPage: (i, url, count) => ...
})
```

- 记住原 URL → 逐页 `chrome.tabs.update` → 等 `complete` + 600ms 渲染 → 读 DOM
- **连续 3 页空即停止**（SPA 读不到总页数，靠这个收敛，不会真跑 40 页）
- 全部完成后 `tabs.update` 导航回原 URL
- 每页回调 `onPage`，供上层打日志/上报进度

### 2. `buondua-service.ts`：批量分支（不再逐页调用）

```ts
if (domFetchFn && site.def.domFallback) {
  const imgTags = (firstHtml.match(/<img\b/gi) ?? []).length
  if (imgTags === 0) {
    // 一次性把 all（全部页 URL）交给 DOM 通道
    const pageResults = await domFetchFn(all, containerSel, hosts, onPage)
    // 汇总去重后直接 return，不进 HTML 循环
  }
}
```

**为什么必须批量**：逐页调用意味着每页都要单独走一遍「导航 → 等待 → 提取」，且早期实现每页还重新开/关标签页。批量后一个导航上下文处理所有页，开销与页数线性但无重复建立成本。

同时**删除循环内的旧降级块**（已被批量分支取代，且签名已变）。

### 3. `background.ts`：`domFetch` 改为批量语义

```ts
const domFetch = async (urls, selector, hosts, onPage) =>
  await extractPagesByTabNavigation(message.srcTabId, urls, {
    selector, hosts, stopAfterEmptyPages: 3, onPage,
  })
```

## 五、取舍说明

| 项 | 说明 |
|----|------|
| 占用当前标签页 | 抓取期间会逐页导航。这是「不被节流」的代价。若你更希望不打断浏览，可改回临时标签页但**必须 `active: true`**（会弹窗闪动），或者接受更慢 |
| 每页约 1~2 秒 | 加载 + 600ms 渲染。11 页约 15~25 秒 |
| 停不下来的风险已消除 | 连续 3 页空即停；即使空壳也最多多跑 3 页 |

## 六、如果仍然卡住

请贴日志。重点看：

- 是否有 `SPA 站点：改走浏览器 DOM 批量通道`（没有说明没进分支）
- `DOM 页抓取` 停在第几页
- 该页的 `count` 是否为 0

若停在某一页且 count 一直是 0，说明该页要么 404、要么渲染更慢（可把 `renderWaitMs` 提到 1200）。
