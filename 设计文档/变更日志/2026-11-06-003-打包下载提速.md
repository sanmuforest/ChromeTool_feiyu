# 2026-11-06-003 打包下载提速：缓存已取字节 + 跳过必失败通道

> 版本：**v0.2.62** ｜ 类型：性能修复（v0.2.61 的副作用）
> 触发：用户反馈「现在虽然能成功下载，但是打包下载速度非常慢」

## 一、现象量化

按日志时间戳计算：

```
00:59:37  相册全量抓取完成（77 张）
01:04:09  打包下载完成 (ok 66/77)
→ 4 分 32 秒 / 77 张 ≈ 3.5 秒/张
```

## 二、慢的三个原因

| # | 原因 | 代价 |
|---|------|------|
| 1 | **同一张图取两遍字节**（v0.2.61 引入） | 显示走 blob 取一次 + 打包走 `GRAB_FETCH_IMAGE` 再取一次 → 请求数翻倍 |
| 2 | **每张先试「源页注入」** | imgbb 图片在 `i.ibb.co`、相册页在 `ibb.co`，**跨子域必然 CORS 失败** → 每张白跑一次往返（日志里每条都有 `TypeError: Failed to fetch`） |
| 3 | **503 退避重试** | 11 张 503 × 3 次重试（800+1600+3200ms）≈ 61 秒 |

其中 **原因 1 是主因**（77 张 × 2 = 154 次取字节）。

## 三、改动

### 1. `src/background/background.ts` —— 跳过必失败的源页注入

```ts
const isImgbbImage = /^https?:\/\/(?:i\.ibb\.co|[^/]*\.imgbb\.com)\//i.test(message.url)
if (message.srcTabId && !isImgbbImage) {
  // 源页注入优先（原有逻辑）
} else {
  buf = await fetchImageBytes(message.url)   // imgbb 直接走 background
}
```

依据：实测 `i.ibb.co` 对任意 Referer（含 `chrome-extension://`）都返回正常大图，页面内 fetch 却因跨子域被 CORS 拦 —— 该通道对该图床**必然失败**，直接跳过。

### 2. `src/grabber/image-grab-view.ts` —— 字节缓存复用

```ts
const blobCache = new Map<string, Blob>()
const BLOB_CACHE_LIMIT = 400
```

- `recoverThumb()`：取字节成功后写入缓存（显示阶段）
- 打包 worker：**先查缓存**，命中则直接 `zip.file()`，**不再发起任何请求**

## 四、预期效果

| 场景 | 改动前 | 改动后 |
|------|--------|--------|
| 已显示过的图（进过视口） | 打包 1 次请求 + 显示 1 次 | **打包 0 次**（缓存命中） |
| 未显示过的图 | 源页注入(必失败) + background = 2 次 | **background 1 次** |

对 77 张的相册：请求数约从 **230+ 次降到 20～80 次**，打包时间预期从 4.5 分钟降到 **数十秒**。

## 五、验证

- `npm run typecheck`：EXIT=0
- `npm run build`：通过（v0.2.62）
- 逻辑审阅：
  - 缓存上限 400 张（77 张相册全命中；700 张级大相册只缓存前 400，其余仍按单次请求处理）
  - 非 imgbb 站点行为不变（仍走源页注入优先，仍走 `<img>` 显示）
  - 缓存命中时 `zip.file()` 直接写入 Blob，不产生网络请求

## 六、用户实测清单

1. **刷新扩展**
2. 重新抓 `https://ibb.co/album/f4npz4`（77 张）→ 先滚一遍让图片显示（写入缓存）→ 再打包
3. 预期：打包明显变快（数十秒内完成）；日志里 `GRAB_FETCH_IMAGE 源页注入失败` 不再出现（imgbb 已跳过该通道）
4. 若不滚动直接打包，仍会逐张取字节（速度居中，属预期）

## 七、未做的优化（避免越界）

- **503 重试策略**未动（仍 3 次 / 800-1600-3200ms）。若你希望打包更快而接受略低的成功率，可以缩短为 500-1000-2000ms 或减少次数 —— 需要你确认后再改。
