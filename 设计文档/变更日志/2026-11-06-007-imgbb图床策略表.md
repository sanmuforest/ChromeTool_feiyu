# 2026-11-06-007 imgbb 图床策略表（降并发 / 短超时 / 快重试）

> 版本：**v0.2.66** ｜ 类型：性能策略（按图床自适应）
> 触发：用户要求「解决 imgbb 的问题」，并反馈网页端也卡顿、相册加载不全，询问 imgbb 模块是否需要独立

## 一、先做客观测量：慢是网站还是本地？

### 同一张图（102612 bytes，内容每次一致，未被降级）

| 方式 | 成功 | 单次耗时 |
|------|------|----------|
| 代理 | 2/3 | 1118 / 2161(失败) / 3945 ms |
| 直连 | 3/3 | 1918 / 1921 / 10499 ms |

### 8 张图：并发 vs 顺序

| 方式 | 总耗时 | 成功 | 失败特征 |
|------|--------|------|----------|
| **并发 8** | 35.5 秒 | **4/8** | 失败的 4 张全部卡到 **30 秒超时** |
| **顺序 8** | 69.6 秒 | 6/8 | 平均 **8.7 秒/张** |

## 二、三条结论

1. **imgbb 服务端本身就慢**：顺序请求平均 8.7 秒/张，单张在 1.1～10.5 秒之间波动
2. **imgbb 对并发极度敏感**：并发 8 张时一半卡到 30 秒超时，顺序反而成功率更高
3. **与本地网络/代理无关**：直连与代理都慢（直连出现过 10.5 秒），且图片字节数每次一致

→ 这也解释了用户说的「**网页端也卡顿、相册加载不全**」：网页端与插件在跟同一个慢服务端打交道。
→ **把插件优化到"很快"是不可能的**，天花板就是 imgbb 的服务端响应速度。

## 三、关于「imgbb 是否需要独立」的判断：**不需要独立**

现状（`设计文档/模块边界.md`）：
- `imgbb-parse.ts`（解析）、`imgbb-service.ts`（服务端编排）、`imgbb-diffuse.ts`（扩散）、`view-adapters.ts`（专属 UI）**本来就是独立模块**
- 唯一与其它场景共用的是 `image-grab-view.ts`（网格/筛选/预览/打包这套通用 UI）

用户观察到的「筛选和反爬有差距」是**准确的**，但那是**策略参数差异**，不是模块划分问题：

| 差异点 | imgbb | 其它站 |
|--------|-------|--------|
| 反爬容忍度 | 极低（并发 8 → 一半超时） | 较高（并发 12 正常） |
| 单张超时 | 1~10 秒波动 | 通常 < 2 秒 |
| 尺寸信息 | 后台解析只给 URL | 部分站有宽高 |

若独立成新模块，网格/筛选/选择/预览/打包代码要复制一份 → 两份维护、改 bug 要改两处，
违反红线 1（模块隔离）与"禁止重复实现"。

**正确做法：共享组件 + 图床策略表** —— 逻辑一份，参数按 host 不同。

## 四、改动

### 1. `src/lib/downloader.ts` —— 新增图床策略表

```ts
export interface HostPolicy {
  concurrency?: number    // 该图床允许的并发上限
  timeoutMs?: number      // 单张取字节超时
  retryMax?: number       // 限流重试次数上限
  backoffBaseMs?: number  // 退避基数
}

const HOST_POLICIES = [
  { re: /^(?:i\.ibb\.co|[^.]*\.imgbb\.com)$/i,
    policy: { concurrency: 3, timeoutMs: 12000, retryMax: 1, backoffBaseMs: 300 } },
]

export function policyForUrl(url: string): HostPolicy
```

`fetchImageBytes()` 改为按策略取 `timeoutMs / retryMax / backoffBaseMs`（未命中策略时沿用原默认值，其它站点行为不变）。

### 2. `src/grabber/image-grab-view.ts` —— 打包并发按策略压

```ts
const CONCURRENCY_RAW = ...   // 全局设置（默认 12）
const imgbbLimit = policyForUrl('https://i.ibb.co/x').concurrency
const hasImgbb = items.some(...)      // 打包内容是否含 imgbb 图片
const CONCURRENCY = hasImgbb ? Math.min(CONCURRENCY_RAW, imgbbLimit) : CONCURRENCY_RAW
```

### 3. `src/lib/downloader.ts` —— 下载路径跳过 imgbb 源页注入

`startOne()` 原逻辑：源页注入 → 失败降级 background（每张白跑一次 CORS 失败，且无超时约束）。
改为**直接 background fetchImageBytes**，依据同 v0.2.62（实测 i.ibb.co 对任意 Referer 返回原图，非 180 降级）。

`fetchImgbbViaSrcTab()` 标记 `@deprecated`，保留定义避免与历史记录失联，不再被调用。

## 五、预期效果

| 指标 | 改动前 | 改动后 |
|------|--------|--------|
| imgbb 打包并发 | 12（大量 30 秒超时） | **3**（按实测最优） |
| imgbb 单张超时 | 40 秒 | **12 秒**（快速失败 → 快速重试） |
| imgbb 重试 | 3 次 × 500/1000/2000ms | **1 次 × 300ms** |
| 下载路径 | 每张先白跑一次 CORS 失败 | 直接取字节 |
| 其它图床 | 不变 | 不变 |

**诚实预期**：受 imgbb 服务端限制，打包 77 张预计仍需 **1.5～2.5 分钟**，但应不再出现"最后几张卡 2 分钟"的极端长尾。
