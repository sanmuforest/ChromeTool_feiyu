# 2026-11-11-001 图床拒绝 fetch 时改走浏览器原生下载

> 版本：**v0.2.72** ｜ 类型：能力降级（绕开 Cloudflare 拦截）
> 触发：用户实测 8se.me 相册抓取 522 张成功，但打包只有 22 张（`ok: 22, total: 522`）

## 一、问题定位

用户日志（v0.2.71）：

```
00:14:03  全子页抓取完成 { count: 522, pages: 40 }   ← 抓取完全成功
00:12:38  打包下载完成 { ok: 22, total: 522 }        ← 打包只成 22 张
```

失败全部集中在 `img.xchina.io`（8se.me 与 xchina 共用图床），两条取字节通道都不可用：

| 通道 | 错误 | 原因 |
|------|------|------|
| 页面内 fetch（`fetchViaSrcTab`） | `TypeError: Failed to fetch` | 跨子域（`tw.8se.me` → `img.xchina.io`），被 CORS 拦 |
| 后台 fetch（`fetchImageBytes`） | `HTTP 403` | Cloudflare WAF 拦（实测 `Server: cloudflare`、`CF-Ray: ...-HKG`、空响应体） |

**但同一 URL 用 `<img>` 能正常显示** —— 说明浏览器原生请求栈能过 Cloudflare，只有 fetch 不行。
这也解释了为什么「下载选中」（走 `chrome.downloads`）比打包好用。

## 二、改动（`src/grabber/image-grab-view.ts`）

打包流程新增**原生下载分支**：

```ts
const NATIVE_DL_RE = /^https?:\/\/img\.xchina\.io\//i
const nativeItems: DownloadItem[] = []
```

| 阶段 | 行为 |
|------|------|
| 阶段 1（并发 worker） | URL 命中 `NATIVE_DL_RE` 的**不试 fetch**（100% 失败且要等超时），直接收集到 `nativeItems`；其余照旧 fetch → ZIP |
| 阶段 2（失败集中重试） | 不变（只处理 fetch 失败项） |
| **阶段 3（新增）** | 对 `nativeItems` 逐个 `chrome.downloads.download`，**每张间隔 60ms** 降低触发图床限流的概率；统计 `nativeOk` / `nativeFail` |

**为什么是「另存」而不是「进 ZIP」**：ZIP 需要字节数据，而 `chrome.downloads` 是直接落盘、不返回内容。所以这些图不打包，改为单独下载到同一文件夹。

**提示文案**也同步更新，避免用户以为漏图：

- 全部走原生下载时：`无图可打包；已用浏览器原生下载 N 张（全部成功 / 失败 M 张）`
- ZIP + 原生混合时：`打包完成：ZIP 内 X 张；另用浏览器原生下载 N 张（该图床拒绝打包读取）`

- **构建产物核对**：`dist/js/grabber.js` 中能搜到 `const NATIVE_DL_RE = /^https?:\/\/img\.xchina\.io\//i`，确认新逻辑已进入打包结果

## 五、已知限制与风险

| 项 | 说明 |
|----|------|
| **不入 ZIP** | `chrome.downloads` 拿不到字节，无法打包。这批图是零散文件，不是压缩包 |
| **仍是逐个下载** | 522 张会产生 522 个下载任务，浏览器下载列表会很长 |
| **可能仍触发限流** | 60ms 间隔是按「实测 22 张即触发」调得很保守的值，但如果 Cloudflare 按**累计流量**而非频率计，下到一定量仍会失败。若出现大量 `浏览器原生下载失败`，下一步改为可配置间隔（如 300~500ms） |
| **尺寸仍未知** | 原图尺寸需要读字节（fetch），被 403 拦死，无法获取。这个站只能一直显示「尺寸未知」 |
| **文件名** | 用 `item.filename`，与 ZIP 内命名规则一致 |
