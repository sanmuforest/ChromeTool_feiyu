# Chrome Web Store 发布

从构建产物到商店上架的完整流程。

## 打包准备

1. `npm run build` 产出 `dist/`
2. 检查清单：
   - `manifest.json`：name/version/description 正确，`action` 图标齐全
   - 无 console 调试输出，无 `localhost`/开发地址残留
   - 图标 16/32/48/128 齐全且非占位图
   - 包内无 `.map` 源码映射（可选保留，但会暴露源码）
3. 压缩为 **zip**（压缩包根目录含 `manifest.json`，不要嵌套文件夹）
4. 版本号遵循 semver，`version` 与商店版本一致

## 上架素材

| 素材 | 要求 | 建议 |
|------|------|------|
| 图标 | 128×128 PNG | 清晰、辨识度高，不含文字水印 |
| 截图 | 1280×800 或 640×400 | 展示真实界面 + 使用场景，1~5 张 |
| 宣传图 | 440×280（可选手动上传） | 品牌化 |
| 描述 | 简洁英文为主 | 首段 132 字符内讲清价值；中文可补充 |
| 隐私政策 | 收集数据则必须 | 说明收集内容、用途、联系方式 |

## 审核合规自查（对应 security skill）

- 单用途清晰，描述与功能一致
- 权限最小化，无隐藏行为
- 无远程代码、无混淆隐藏逻辑
- 数据收集有告知与删除途径

## 上架流程

1. 注册 Chrome Web Store 开发者账号（一次性 $5）
2. 新建项目 → 上传 zip → 填写商店信息
3. 提交审核（通常 1~7 天；首次或含权限变更可能人工审核更久）
4. 审核反馈处理：按拒审原因逐条修复后重新提交
5. 上架后关注：用户评分、错误报告（`chrome://extensions` 错误页统计思路）、活跃度

## 版本迭代

- 每次发版更新 `version`（`x.y.z`），商店与 manifest 同步
- 重大变更（新增权限）会触发再次人工审核，提前规划
- 灰度策略：先发布到测试渠道（`chrome://extensions` 本地加载验证）再全量
- 变更日志维护在 `变更日志/`，商店描述同步更新

## 多浏览器扩展

- **Edge Add-ons**：直接复用 Chrome zip，流程类似（微软开发者中心，免费）
- **Firefox AMO**：需适配 MV3 差异（`browser` API、`storage` 事件名），单独构建
- 原则：Chrome 优先，Edge 顺带，Firefox 按需
